## Rebuilding a machine

I keep the repo at `~/dotfiles`:

``` bash
git clone https://github.com/4evy/dotfiles.git ~/dotfiles
cd ~/dotfiles
```

<details>
<summary><strong>Spectrum / Bluefin</strong></summary>

<br>

On a fresh Bluefin install, I switch to the Spectrum image:

``` bash
sudo bootc switch ghcr.io/4evy/spectrum:latest
systemctl reboot
```

After the reboot, I finish the setup:

``` bash
cd ~/dotfiles
just setup
```

</details>

<details>
<summary><strong>NixOS</strong></summary>

<br>

On an installed NixOS system, I apply the flake and finish the shared setup:

``` bash
sudo nixos-rebuild \
  --option extra-substituters https://install.determinate.systems \
  --option extra-trusted-public-keys cache.flakehub.com-3:hJuILl5sVK4iKm86JzgdXW12Y2Hwd5G07qKtHTOcDCM= \
  --flake .#nixos \
  switch
just setup
```

The extra cache options are only needed for the first rebuild. Afterward, this
shorter command is enough:

``` bash
sudo nixos-rebuild switch --flake .#nixos
```

</details>

<details>
<summary><strong>macOS</strong></summary>

<br>

Requires macOS 27 or newer. From the cloned repo, I run:

``` bash
tools/setup/setup.sh setup
```

The script asks for administrator and 1Password access when needed

</details>

Multiword commands use spaces, such as `just records edit` and
`just spectrum build`. Run `just --list --list-submodules` to list commands,
or `just help <command> [subcommand...]` for usage.

Records commands run [the TypeScript CLI](tools/records/main.ts) with Bun
through `just records`. The SOPS vault and protected workspace formats are
unchanged. Run `just records check` to validate the vault,
`just records unpack` to materialize editable sources, and `just records pack`
to encrypt changes and conceal the plaintext again

[Theme-run](tools/theme/run/main.ts) is also TypeScript. Its Nix package
compiles a standalone executable with Bun. Go remains installed for general
development but is no longer required to build this repository's programs

## Source layout

I group source files by responsibility:

| Directory            | Responsibility                                               |
| -------------------- | ------------------------------------------------------------ |
| `data/`              | Shared platform, package, and deployment inventories         |
| `home/files/`        | Native home-relative configuration sources                   |
| `home/applications/` | Personal application settings and reconciliation             |
| `home/deploy/`       | Home rendering, generation, activation, and checks           |
| `home/theme/`        | Shared personal appearance policy                            |
| `systems/`           | Host composition, system modules, and Spectrum image sources |
| `tools/`             | First-party programs, installers, setup, and update tooling  |
| `packages/`          | Upstream software customizations and package recipes         |
| `nix/`               | Flake composition, overlays, and development infrastructure  |
| `lib/`               | Implementation shared by multiple components                 |
| `just/`              | Public command entrypoints                                   |
| `secrets/`           | Encrypted records and settings                               |

I use lowercase directory groups for source names, such as
[`data/homebrew/tools.json`](data/homebrew/tools.json) and
[`nix/lib/gnome/defaults.nix`](nix/lib/gnome/defaults.nix), rather than joining
responsibilities with camelCase or hyphens. Native application paths, upstream
names, tool-required filenames, and numbered startup fragments keep their
required spelling. Source-only moves preserve deployed targets in
[`home/manifest.nix`](home/manifest.nix)

The root `recipes` symlink points to `systems/spectrum/recipes` because the
pinned BlueBuild CLI resolves recipe imports through that entrypoint

I keep palette role mappings and numeric parameters in
[`home/theme/palette/`](home/theme/palette/). After editing those inputs, I run
`bun home/theme/palette/generate.ts` to regenerate `palette.json`. Tiling
shortcuts live in [`tools/tiling/bindings.json`](tools/tiling/bindings.json),
and workstation defaults live beside their consumers under
[`tools/workstation/`](tools/workstation/)

I edit shared GNU tool policy in
[`data/homebrew/tools.json`](data/homebrew/tools.json). It feeds Homebrew,
bootstrap selection, and shell paths. Darwin keeps the
[Brewfile's source closure](systems/modules/darwin/applications.nix) intact
so its relative JSON imports also work from the Nix store

TypeScript entry points compose Effect programs through
[`lib/typescript/runtime.ts`](lib/typescript/runtime.ts). Pure transformations
stay independent of I/O. The native KWin adapter is an explicit exception
because Qt's JavaScript engine lacks the BigInt support Effect requires

The root [`package.json`](package.json) declares the packaged activation and
hardware commands in `bin`. The root [`package.nix`](package.nix) reads that
mapping to bundle and wrap each command

Cross-directory TypeScript imports use scoped package exports, such as
`@dotfiles/core/commands` and `@dotfiles/home/palette`. Export boundaries live
in the package manifests for [core](lib/typescript/package.json),
[home](home/package.json), [workstation](tools/workstation/package.json), and
[tiling](tools/tiling/package.json). Sibling imports stay relative

Deployed scripts share the
[`@dotfiles/runtime` package](home/files/.local/lib/package.json) at
`~/.local/lib`. Its exports resolve without the checkout or a TypeScript path
alias. Checkout packages share the root workspace lock, while the deployed
runtime retains its own lock. `just bun install` installs the workspace

For a standalone workstation install, I use
`sh tools/workstation/install.sh`. The shell entry point installs frozen
dependencies before loading TypeScript, including on a fresh checkout
